# Инженерный справочник по портированию, моддингу и сохранению игр

**Редакция:** 5 ноября 2026 г., версия 2.0. **Аудитория:** Windows-хост, собственная PS4 Pro с GoldHEN и Honor X8c (ARM64, Snapdragon 685 / Adreno 610). Примеры предназначены для собственных приложений, разрешённых модов, **офлайновой одиночной игры** и изолированного сохранения игр. Никаких атак на действующие коммерческие серверы, обхода античита/защит, распространения ключей, прошивок, игр или чужих сохранений. Законность зависит от юрисдикции и лицензии; используйте собственные копии и проверяйте лицензии исходных проектов.

> **Не универсальная кнопка «портировать».** Распознавание эвристическое; образцы JSON и байтов искусственные. Инструмент не расшифровывает SELF/FSELF, FairPlay, Denuvo, APK, ресурсы или сетевой трафик. Нельзя выводить реальное назначение адреса, работоспособность чита или совместимость игры только по совпадению сигнатуры. Ни консоль, ни телефон в этой среде не тестировались.

## 0. Практический старт и инвентаризация

1. Запишите название и **регион/CUSA, версию игры**, платформу, версию движка, ABI, размер и SHA-256 каждого файла. Отдельно сохраните исходные файлы и сохранения. Не работайте с единственной копией.
2. Убедитесь, что необходимая функциональность действительно автономна и работает без действующих сетевых служб. Если нет — ограничьтесь архитектурным анализом, а не подключением к публичной инфраструктуре.
3. Windows: установите Python 3.10+, из корня набора выполните `py -m pip install -r requirements.txt` и `py tools/re_swiss_knife.py --analyze "D:\Games\MyGame"`. Linux/macOS: `python3` вместо `py`. У Capstone есть бинарные зависимости; наличие подходящего wheel зависит от платформы.
4. Телефон: указанный SoC использует AArch64 и Adreno 610; обычный Android-приложение не обязано поддерживать системные кастомные графические драйверы. Mesa Turnip — реализация Vulkan для Adreno, доступность конкретного драйвера, возможности загрузки и совместимость зависят от ОС, устройства и приложения. Это **не** гарантия запуска Direct3D-игры.
5. PS4 Pro: Orbis OS — производная от FreeBSD 9, а не обычный desktop FreeBSD; CPU x86-64 не отменяет различий в ABI, графических API, системных вызовах и SDK. [OpenOrbis](#источники) — открытый homebrew-toolchain, **не** официальный Sony SDK.
6. После каждого шага фиксируйте оригинал, изменения, метод отката, ожидаемые и фактические результаты. Для сохранений сначала создайте резервную копию через Apollo, затем проверьте её восстановление на тестовой копии.

### Что можно и нельзя определить за 10 секунд

| Признаки | Вывод и оговорки |
|---|---|
| `UnityPlayer`, `*_Data`, `globalgamemanagers` | Вероятно Unity; backend ещё неизвестен. |
| `global-metadata.dat` вместе с `GameAssembly.dll` / `libil2cpp.so` | Вероятно Unity IL2CPP нужной сборки. Файл metadata без пары недостаточен. |
| `MonoBleedingEdge`, `Managed/Assembly-CSharp.dll` | Вероятно Unity Mono; остатки и файлы модов могут давать ложные совпадения. |
| `Content/Paks`, `.uasset`, `.pak` | Возможен Unreal; одни лишь `.pak` не уникальны для UE. |
| `.utoc` + `.ucas` | IoStore, но это встречается и в UE4.25+, и в UE5. Номер UE5 должен подтверждаться версией/другими признаками. |
| `gameinfo.txt`, `*_dir.vpk` | Source или производный движок; VPK отдельно не доказывает версию. |
| `.toc` с `.sb`/`.cas`, строка Frostbite | Возможен Frostbite, формат отличается по игре и версии. |
| `project.godot`, Godot runtime | Godot; версия проекта должна совпадать с экспортом. |
| `renpy/`, `.rpy`/`.rpyc`, `.rpa` | Вероятно Ren'Py. |
| Нет признаков | Неизвестно, **не доказано**, что движок собственный C++. |

Анализатор показывает доказательства и уверенность, а не только название. При сканировании APK/IPA он читает ZIP-оглавление и ограниченные префиксы кандидатов без извлечения; APK может содержать несколько ABI. По умолчанию до 30 000 файлов/элементов и до 100 бинарных кандидатов; строки/заголовки анализируются в первых 2 МиБ. Упакованные/зашифрованные записи, пропущенные файлы, урезанные таблицы и ложные совпадения не позволяют утверждать отсутствие признака.

```powershell
py tools/re_swiss_knife.py --analyze "D:\Games\MyGame"
py tools/re_swiss_knife.py --analyze "C:\Copies\game.apk" --json
py tools/re_swiss_knife.py --analyze "C:\Copies\eboot.bin"
```

**Форматы и ограничения.** `7F 45 4C 46` — ELF, CPU определяется полем `e_machine` и порядком байтов; `MZ` проверяется вместе с PE-заголовком. NSO начинается `NSO0`, однако сама эта сигнатура **не кодирует CPU**: AArch64 часто встречается на Switch, но не доказан; сегменты могут быть сжаты. PS4 SELF/FSELF имеют little-endian bytes `4F 15 3D 1D` (`0x1D3D154F`); по одной магии нельзя установить fake-signature или реальную степень шифрования. Обычный ELF — другая форма, но его наличие не устанавливает происхождение или разрешение на использование. Mach-O `LC_ENCRYPTION_INFO[_64].cryptid != 0` — признак шифрования данного slice; `cryptid == 0` относится только к указанной команде, а отсутствие команды или недоступный slice оставляет статус неизвестным. Подстрока `Denuvo`, `.vmp*`, `.upx*` — лишь признаки, а не надёжный тест установленной/активной защиты. Наличие `.symtab`, DWARF, PDB-строк или строк компилятора тоже не обещает полную таблицу символов.

# 1. Портирование: три маршрута

## 1.1 Выбор метода

```text
Имеется исходный код / SDK игры? ── да ──► нативный порт и перекомпиляция
            │ нет
            ▼
Код готового движка можно заменить? ─ да ─► независимая реализация + свои данные
            │ нет
            ▼
Есть рабочий guest ISA/ABI и разрешённые данные?
  ├─ статическая рекомпиляция: guest инструкции → C/C++ + runtime
  └─ динамический перевод / ABI wrapper: guest код → выполнение + мост API
```

| Подход | Что сохраняется | Недостающая работа | Типовой риск |
|---|---|---|---|
| Нативный порт исходников | алгоритмы, структуры проекта | сборка, платформенный слой, графика, ввод, ассеты | зависимость от SDK и лицензий |
| Static recomp | поведение известных инструкций | адресное пространство, вызовы ОС/GPU, файлы, тайминги, исключения, косвенные переходы | неизвестные функции/данные в коде, self-modifying/JIT |
| Dynamic translation / wrapper | исходный машинный код | перевод ISA при необходимости; ABI/линкер/импорты, системные сервисы | сложность отладки, производительность, несовпадение ABI |
| Engine recreation | собственная новая реализация | формат данных, игровой цикл, все подсистемы | полнота и точность поведения; правовой статус форматов/данных |

Проверяйте лицензии инструмента, исходников и данных отдельно. Не переносите закрытые библиотеки и контент в публичные артефакты. Любая технология ниже — материал для анализа совместимости, не средство обхода лицензирования.

## 1.2 Static recomp: контекст регистров и косвенный поток

[XenonRecomp, R1](#источники) буквально переводит инструкции PowerPC Xbox 360 в C++ и передаёт каждой функции `PPCContext` и указатель на базу guest-памяти. В контексте хранятся регистры общего назначения, условные поля и векторные/FPU состояния. Guest big-endian загрузки/записи должны сохранять нужный порядок; точность float/vector, ограничения ABI, атомарность и порядок памяти важны. Проект прямо предупреждает, что **сам не предоставляет готовый runtime**.

```text
guest XEX + символы/границы + таблицы переходов
            │
            ▼
     функция guest: sub_1234
            │  инструкция → эквивалент C++
            ▼
void sub_1234(PPCContext& ctx, uint8_t* guest_base) {
    // псевдокод: ctx.r3 = load_guest_u32_be(guest_base, ctx.r4);
}
            │
            ├── прямой вызов → соответствующая recompiled-функция
            ├── адрес из регистра → таблица guest адрес → host функция
            └── обращения к ОС/GPU → отдельно реализованный runtime
```

По README XenonRecomp для indirect functions применяется таблица соответствия адресов, а распознанные таблицы `mtctr`/`bctr` преобразуются в `switch`; полностью общего алгоритма для jump tables нет. Нужно исследовать границы функций, код/данные и вручную отмечать пропуски. В [N64Recomp, R2](#источники) MIPS `jalr` становится `LOOKUP_FUNC(ctx->r25)(rdram, ctx)`, а runtime отслеживает размещение overlays; delay slot учитывается отдельно. Эти детали зависят от ISA и не делают один рекомпилятор универсальным для PS4, Android и Switch.

**Порядок работ:**

1. Документируйте законный источник бинарника и данных; определите ISA, порядок байтов, ABI, разделы, символы, entry points и формат загрузки. Составьте карту функций/адресов, а не просто дизассемблируйте весь файл как код.
2. Найдите таблицы указателей, косвенные ветвления, overlays, relocations и внешние вызовы. Сопоставьте их со статическим CFG; сравните трассы собственного тестового запуска, если это разрешено.
3. Постройте регистровый контекст и guest memory: диапазоны, endianness, выравнивание, запрет выхода за границы, инструкции SIMD/FPU и исключения. Должен быть тест на каждую семантику.
4. Сделайте ABI-мост для файлов, потоков, часов, аудио, ввода и рендера. Таблица переходов должна отказывать на неизвестном guest-адресе, а не прыгать по произвольному указателю.
5. Соберите host-бинарник; сравнивайте контрольные значения и трассы с эталоном, вводите золотые тесты, профилируйте. Переход на телефон/PS4 возможен **только после** реализации runtime и подгонки платформенного слоя.

## 1.3 Динамический перевод и loader-wrapper

[Box64, R3](#источники) исполняет **Linux x86-64 userspace** на поддерживаемых 64-битных Linux-хостах и может использовать dynarec и нативные системные библиотеки (например, SDL). Он не является прямым загрузчиком Windows `.exe`, и наличие ARM64-телефона не гарантирует работоспособность; для Windows-программ требуется дополнительная совместимая среда вроде Wine, подходящие драйверы и проверка лицензий. Android использует Bionic, linker namespaces, свой lifecycle и политики памяти; desktop glibc и произвольные `.so` не становятся совместимыми простым `dlopen`.

[gtasa_vita, R4](#источники) — **Vita-порт Android ARMv7-библиотеки**, не Android ARM64 loader и не пример переноса x86 на ARM. `loader/so_util.c` отображает сегменты 32-битного ELF, обрабатывает выбранные ARM relocations, разрешает символы и запускает инициализацию; остальной проект мостит Android API/графику к Vita. Это пример серьёзной работы над конкретной версией/ABI, а не универсальный loader.

```text
Собственное Android-приложение (arm64-v8a)
  ├─ Bionic linker: dlopen → DT_NEEDED, relocations, init_array
  ├─ ABI bridge: libc, JNI/Android lifecycle, звук/ввод/файлы
  └─ renderer: SDL2 + Vulkan/OpenGL ES → драйвер устройства
```

Минимальный **same-ABI** пример для своей библиотеки, не переводчик архитектуры:

```cpp
#include <dlfcn.h>
#include <cstdio>
// libgame.so должно принадлежать приложению, быть доступно linker namespace
// и иметь тот же ABI; объявленная функция должна существовать.
int run_owned_library() {
    void* h = dlopen("libgame.so", RTLD_NOW | RTLD_LOCAL);
    if (!h) { std::fprintf(stderr, "%s\n", dlerror()); return -1; }
    using Init = int (*)();
    dlerror();
    auto init = reinterpret_cast<Init>(dlsym(h, "game_init"));
    if (const char* e = dlerror()) { std::fprintf(stderr, "%s\n", e); dlclose(h); return -2; }
    int rc = init();                 // никакой API не гарантирован заранее
    dlclose(h);                      // только после прекращения использования функций
    return rc;
}
// Линковка своей NDK-сборки: -ldl
```

При собственной реализации загрузчика необходимы: проверка заголовка и диапазонов `PT_LOAD`, `mmap`/выравнивание, нулевая BSS-часть, соответствующие конкретной архитектуре relocation/PLT/GOT, TLS, символы, конструкторы и корректные разрешения страниц. Разбор формата **не** предоставляет права и средств расшифровки. Небезопасно отображать непроверенные сегменты с RWX или брать произвольные адреса из файла.

## 1.4 Пошаговый перенос на Android и PS4

**Общий маршрут:** инвентаризация → маленький воспроизводимый запуск → слой ОС/файлов → renderer → ввод/звук → сборка тестов → профилирование → отдельная упаковка своих данных. Фиксируйте выходной ABI и ограничения памяти на каждом шаге.

**Android / Honor X8c:**

1. Установите Android Studio + NDK и подходящие CMake/Ninja. Начните с собственного `arm64-v8a` теста. Если исходник только ARMv7/x86-64, его нельзя связать с ARM64-процессом: нужен исходный код либо отдельная подходящая среда выполнения/перевод.
2. Организуйте SDL2 activity/lifecycle, JNI и собственный shared library; работайте через `AAssetManager` или разрешённый app storage, учитывая Android scoped storage. Нельзя считать `fopen` единственным путём чтения APK assets.
3. Выберите GLES/Vulkan или переносимый renderer. Direct3D/PS4 GNM/GNMX — другие API; трансляционный слой должен отдельно реализовать шейдеры, синхронизацию и форматы текстур. На Adreno проверяйте реальные расширения и лимиты, а не только название GPU.
4. Соберите и установите только своё приложение; тестируйте потоки, периоды сна/возврата, контроллер, память, нагрев и несколько графических драйверов. Скомпилированный библиотечный шаблон из комплекта не внедряется в чужой процесс автоматически.

**PS4 / OpenOrbis:**

1. Установите release OpenOrbis и clang/lld, задайте `OO_PS4_TOOLCHAIN` согласно [R5](#источники), соберите имеющийся hello-world/SDL2 sample без чужого кода.
2. Перенесите **исходники** или собственный runtime: замените Win32/Bionic системные вызовы, файловые пути, графический backend, ввод, звук и сетевые зависимости на совместимые интерфейсы. На PS4 x86-64, но Windows PE или Linux ELF от этого не превращается в корректный Orbis homebrew.
3. Для собственного homebrew используйте документацию toolchain по ELF/SELF и упаковке; Fake PKG — формат установки в соответствующей среде, а не автоматический конвертер любой игры. Тестируйте на совместимой законно настроенной консоли; не включайте игры/SDK/ключи в пакет проекта.
4. Для modding существующей игры предпочитайте поддерживаемые файлы-моды и AFR (§2.4), отдельно проверяйте версию и права доступа. Не смешивайте адреса retail и переработанных исполняемых файлов.

# 2. Движки, ресурсы и VFS

## 2.1 Unity: Mono и IL2CPP

**Mono** хранит управляемые сборки (`Managed/*.dll`); метаданные типов и IL обычно можно изучать в ILSpy. Для поддерживаемого desktop Unity Mono используйте совместимый по версии [BepInEx, R7](#источники) и документированные plugin hooks. Не следует считать, что его стабильный desktop-дистрибутив работает на PS4 или ARM64 Android: сверяйте матрицу конкретного релиза. На IL2CPP исходный IL игры в готовом runtime не появляется автоматически.

**IL2CPP**: управляемые типы и методы преобразованы в native-код; метаданные и код находятся в разных сущностях. `global-metadata.dat` обычно имеет little-endian magic `AF 1B B1 FA` (`0xFAB11BAF`) и версию формата, но упаковка/расположение различаются. Получите **совпадающую** пару файлов и версию Unity. `Il2CppDumper.exe <GameAssembly.dll-or-libil2cpp.so> <global-metadata.dat> <out>` по [R6](#источники) создаёт `dump.cs`, `script.json`, `il2cpp.h`, скрипты для дизассемблеров и `DummyDll`. Последние восстанавливают описание типов, но **не тело исходных методов**.

```text
metadata: имена, типы, методы, индексы, строки
                  │            сопоставление по версии/регистрациям
                  ▼
native image: Il2CppMetadataRegistration / Il2CppCodeRegistration,
              таблицы указателей, native method bodies, relocations
                  │
                  ▼
отчёт инструментов → исследование функции → проверка в своей сборке
```

Регистрации, layout таблиц и generic/shared методы меняются с версией, символы могут отсутствовать, указатель может быть нулём или требовать relocation. Приведённая схема концептуальна; не каждый метод отображается на уникальную функцию. Сопоставьте offset с `PT_LOAD` и ASLR; не копируйте адрес от другой платформы. Зашифрованная/защищённая metadata, чужие ключи и обход защиты находятся вне набора.

**Ресурсы.** [UABE, R8](#источники) редактирует `.assets` и AssetBundles ряда версий, [AssetRipper, R9](#источники) анализирует/экспортирует данные, но экспорт не всегда обратим. Для новых форматов проверьте подходящую версию инструмента. Сохраните `pathID`, ссылки и типы, размеры и импорты; заменяйте ассет на копии, сверяйте текстурный формат, endianness и зависимости. Изменённый ассет нередко нужно заново собрать именно для целевой платформы. Публичный мод должен содержать ваши изменения, а не чужой оригинал.

## 2.2 Unreal Engine 4/5: PAK и IoStore

```text
PAK (концептуально; layout меняется по версии):
  [payload: отдельные файлы/сжатые блоки] [index: path → offset/size/метод] [footer: версия/index/hash/...]

IoStore (упрощённо):
  .utoc  ──► список chunk ID, offsets/длины, compression blocks, метаданные
  .ucas  ──► данные chunks/блоков, иногда разделённые на контейнеры/части
  .uasset/.uexp/.ubulk ──► сериализованные объекты/экспорты/bulk data, где применимо
```

Индекс/блоки могут быть сжаты, подписаны или зашифрованы; таблица выше — **не** спецификация единой версии. В исходнике [repak, R21](#источники) `Footer` хранит magic, версию, `index_offset`, `index_size`, hash и зависящие от версии флаги/методы; `Entry` — offsets, размеры и описания блоков. Repak сначала читает индекс, а данные запрашивает по мере необходимости; [u4pak, R22](#источники) описывает footer → index → data и поддерживает только заявленные версии незашифрованных архивов. Каталог/индекс и число/смысл полей зависят от версии, поэтому всегда сверяйте ограничения конкретного инструмента. IoStore не доказывает UE5: [UnrealPakViewer, R11](#источники) описывает `pak/ucas` и перечисляет сборки UE4. Для принадлежности версии проверяйте метаданные сборки/символы и совместимость инструмента. [UAssetGUI, R10](#источники) редактирует низкоуровневые `.uasset`/`.umap`, а не автоматически пересобирает произвольную зашифрованную игру.

Рабочий цикл: (1) версия и hash; (2) распаковать **доступный незашифрованный** материал на копии подходящим инструментом; (3) исследовать имена, типы, imports/exports, registry и зависимости; (4) приготовить свой ресурс в той же версии UE и **cook для целевой платформы**; (5) упаковать в поддерживаемый мод-контейнер/loose override; (6) проверить порядок монтирования, зависимости, контрольные суммы и откат. Ассет Windows может не подходить PS4/Android из-за формата/шейдеров. Ключи и обход проверок не рассматриваются.

## 2.3 Проприетарный архив и сценарии других движков

* **Source:** начинайте с `gameinfo.txt`, mounts и `_dir.vpk`; при наличии официального mod folder сначала используйте его. `.vpk` встречается и у производных движков.
* **Frostbite:** `.toc`/`.sb` и `cas_*.cas` лишь эвристика. Индекс может ссылаться на chunks/bundles, а сжатие, платформа и версия различаются. Работайте только с доступными данными и документированным форматом.
* **Godot:** `project.godot`/PCK и версия движка помогают восстановить структуру своего проекта; .pck может не содержать исходники. Нужны совместимые export templates и renderer.
* **Ren'Py:** каталоги `renpy`/`game`, `.rpy`, `.rpyc`, `.rpa` — признаки. Предпочтительнее исходный проект и поддерживаемые моды; версия bytecode и архива важна.
* **Custom:** вычисляйте entropy только как признак сжатия/шифрования, проверяйте magic, таблицу файлов, offsets, alignment, сжатие, hash и byte order. Измерения должны быть воспроизводимыми: сравнивайте две разрешённые версии с одним известным изменённым ресурсом. Без подтверждения не объявляйте случайную таблицу имен архивом конкретного движка.

## 2.4 AFR PS4 и файловые перехваты Android

В исходниках [GoldHEN AFR, R12](#источники) перехватываются `sceKernelOpen`, `sceKernelStat`, `fopen`. Для `/app0/<путь>` плагин пробует `/data/GoldHEN/AFR/<titleid>/<путь>`; при неудаче выполняется исходная операция. Например, **искусственный** `/app0/data/ui/logo.bin` может соответствовать `/data/GoldHEN/AFR/CUSA12345/data/ui/logo.bin` на совместимой конфигурации. Настройку и версию плагина проверяйте по его документации; корректный CUSA и точный путь обязательны.

```text
игра: open("/app0/data/ui/logo.bin")
           │
           ├─ существует AFR/<CUSA>/data/ui/logo.bin? ─ да ─► возвращается мод
           └─ нет / не удалось открыть ────────────────────► исходный файл
```

Это не универсальный перехват всей VFS: чтение из уже открытого монолитного архива, прямые системные/другие вызовы, собственные caches, mmap или проверка целостности могут иметь иной путь. Отдельно учитывайте пути, права, размер и зависимости. На Android для своей программы можно явно сделать `open_overlay(name)` с проверкой allowlist/канонизацией и fallback; `fopen`/`open` не заменяют `AAssetManager`. Избегайте рекурсивного вызова перехваченной функции и traversal (`..`); не создавайте автоматический инжектор.

Изменяются только явные файловые атрибуты `path`, `file`, `filename`, `src` и `value` с соответствующим `id`; `from`/`to` — только если значение сопоставляется с фактическим локальным файлом/каталогом, включая ссылки без расширения. Виртуальные идентификаторы, комментарии, посторонние значения, URL и entity-ссылки сохраняются; проверяйте скин вручную. Другие XML-файлы не переписываются. В обоих режимах существующий выход не перезаписывается; лимит результата по умолчанию 1024 МиБ, `--max-output-mb N` позволяет 1–16384 МиБ.

# 3. Офлайновые патчи, AOB, GoldHEN и ARM64

## 3.1 Три вида адресов

```text
ФАЙЛ                     ЗАГОЛОВОК ELF                 ПРОЦЕСС
+------------------+     PT_LOAD p_offset = 0x100      dlpi_addr / load bias
| данные до 0x100  |     p_vaddr  = 0x1100             + image VA (не всегда + RVA)
| код на 0x120     | ──► VA = 0x1100 + (0x120-0x100) = 0x1120
+------------------+     image base = 0x1000            RVA = 0x1120 - 0x1000 = 0x120
```

Для PE `RVA = section.VirtualAddress + (file_offset - PointerToRawData)`; preferred VA = `ImageBase + RVA`, но ASLR может выбрать другую базу. В ELF виртуальный адрес определяется соответствующим `PT_LOAD`, RVA в нашем отчёте — относительно минимального выровненного `p_vaddr` загружаемых сегментов. Для реально отображённого ELF runtime VA обычно `load bias + image VA`; понятия base и bias не взаимозаменяемы. Данные BSS не имеют файловых байтов; overlapping segments могут давать неоднозначное отображение. SELF, сжатый NSO и universal Mach-O этим CLI в адреса автоматически не переводятся.

**GoldHEN offset в конкретном процессе/версии необходимо проверить отдельно.** В v2 для little-endian x86-64 ELF64 без `--goldhen-offset` вычисляется **кандидат**, не подтверждённый runtime-адрес:

```text
base_vaddr = min(p_vaddr) для ВСЕХ PT_LOAD
vaddr = p_vaddr выбранного сегмента + (file_offset - p_offset)
кандидат GoldHEN = vaddr - base_vaddr
```

Это намеренно отличается от показанного выше выровненного RVA: для `p_offset=0x100`, `p_vaddr=0x1100`, `file_offset=0x120` кандидат равен `0x1120 - 0x1100 = 0x20`, а выровненный RVA — `0x120`. Весь диапазон патча должен находиться в одном file-backed `PT_LOAD`, без пересечения с другим `PT_LOAD`; ошибки заголовка, BSS и неоднозначность приводят к отказу. Формула, поля сегмента, file offset, VA и результат печатаются и сохраняются в `patch_metadata.json`. Только файл `CUSAxxxxx_01.00.json` копируют в каталог GoldHEN; metadata храните отдельно. Формула **не доказывает**, как версия GoldHEN выбирает базу конкретного модуля и как влияют ASLR/сборка; проверяйте независимо. Ручной `--goldhen-offset` остаётся override и обязателен для raw dump; он также не проверяется на PS4.


### Распаковка SELF/FSELF и NSO0 перед сканированием

```powershell
python tools/re_swiss_knife.py --unpack-binary "D:\Copies\eboot.bin" --output eboot.elf
python tools/re_swiss_knife.py --unpack-binary "D:\Copies\main.nso" --output main.elf
python tools/re_swiss_knife.py --analyze eboot.elf
python tools/re_swiss_knife.py --scan-aob main.elf --arch arm64 --pattern "1F 20 03 D5"
```

Для SELF [R23](#источники) читаются 32-байтовый заголовок, таблица 32-байтовых entries и вложенный ELF64/program headers. `blocked` указывает связанный program-header index; encrypted flag вызывает отказ. Поддерживаются plaintext и один поток zlib на segment, проверяются размеры, границы, перекрытия и наличие необходимых данных. Сегменты записываются по исходным ELF `p_offset`; отсутствующие ссылки на section table очищаются. Известный необязательный отсутствующий `PT_SCE_VERSION` помечается предупреждением и убирается из файловых данных header. Это **не** расшифровщик retail SELF, и флаги сами по себе не доказывают подлинность или plaintext.

Для NSO [R24](#источники) читаются text/rodata/data descriptors, bss, flags и размеры. Сжатые сегменты декодируются как raw LZ4 реализацией на Python, без `lz4`/C-extension; SHA-256 проверяется, когда соответствующий бит установлен. Отдельный ZBIC и неизвестные/повреждённые форматы отвергаются. Создаётся ELF64 `ET_DYN`, `EM_AARCH64`, с тремя `PT_LOAD`, корректной конгруэнтностью `p_offset/p_vaddr`, правами RX/R/RW и BSS. `e_entry=0`, секций/релокаций и полноценного loader нет. NSO0 не содержит поле CPU — ARM64 здесь **допущение**, а ELF предназначен для анализа, не гарантируется запуск. Offset в синтетическом ELF отличается от offset в сжатом NSO. Исходник и существующий выход не перезаписываются, по умолчанию максимальный результат 1024 МиБ.


## 3.2 Wildcard AOB: теория и работающий учебный пример

AOB — последовательность фиксированных байтов и полных wildcard-байтов (`??` или `?`). `48 89 5C 24 ?? 57` совпадёт с любым значением пятого байта. Найденная позиция — файловый offset, а не доказанная функция. Запрещены all-wildcard и неоднозначный авто-выбор места патча. Pattern должен начинаться на известной границе инструкции, желательно в исполняемом сегменте, и быть уникальным в **каждой** версии; уникальность в одном файле не доказывает семантическую идентичность.

Создайте **искусственный** файл (никакой настоящей игры):

```powershell
py -c "from pathlib import Path; Path('demo.bin').write_bytes(bytes.fromhex('48 89 C0 E8 11 22 33 44 90 C3'))"
py tools/re_swiss_knife.py --scan-aob demo.bin --arch x86_64 --pattern "48 89 C0 E8 ?? ?? ?? ??" --context 8
py tools/re_swiss_knife.py --make-aob demo.bin --arch x86_64 --offset 0x0 --length 8
```

`--scan-aob` ищет все перекрывающиеся совпадения через read-only memory map; `--max-matches N` ограничивает вывод (0 = все). Если установлен Capstone, рядом выводится дизассемблирование; x86 переменной длины, поэтому обратный контекст без известной границы приблизителен. Дизассемблирование от начала совпадения тоже верно только при заранее известной границе. Без Capstone поиск байтов и fingerprint работают, но `--make-aob` сообщает об ошибке.

Генератор читает целые инструкции от заданной границы. В x86-64 он маскирует displacement памяти (в том числе RIP-relative) и immediate прямого относительного `call/jmp/jcc`. ARM64 хранит части immediate и opcode в одном слове: для обычных PC-relative branch/ADR/ADRP/literal и memory displacement консервативно скрывается **целая 4-байтовая инструкция**. Например, простой `?? ?? ?? 94` неверно предполагает, что верхний байт `BL` постоянен: два младших бита этого байта тоже относятся к смещению. Длина ARM64 и offset должны быть кратны 4. Все wildcard-инструкции могут сделать шаблон неуникальным; CLI подсчитает совпадения в этом файле.

Ни один метод не гарантирует переживание обновлений: компилятор меняет порядок инструкций, регистры, non-PC immediate, inline и константы; некоторые relocation/PC-relative случаи невозможно надёжно вывести только из байтов. Используйте дополнительные контекстные признаки, сравнение версий и ручную проверку назначения. Никогда не заменяйте совпадение №1 при наличии нескольких.

## 3.3 Кодировки и безопасный размер патча

Все примеры — little-endian байты **инструкций**, не универсальные читы:

| CPU | Инструкция | Байты | Важно |
|---|---|---|---|
| x86-64 | `nop` | `90` | длина других инструкций переменная; сохраняйте полные границы |
| x86-64 | `mov eax, 9999` | `B8 0F 27 00 00` | запись EAX обнуляет верхние 32 бита RAX |
| ARM64 | `nop` | `1F 20 03 D5` | слово `0xD503201F`, 4-байтовое выравнивание |
| ARM64 | `mov w0, #9999` (`movz`) | `E0 E1 84 52` | слово `0x5284E1E0`, `9999 = 0x270F`, `W0` обнуляет верхнюю половину X0 |
| ARM64 | `ret` | `C0 03 5F D6` | менять поток без понимания ABI/стека недопустимо |

`movz w0,#imm16` для данного примера — `0x52800000 | (0x270F << 5) | 0`; в файле младший байт первым. Для другого регистра/значения/shift используйте ассемблер, не редактируйте пример вручную. NOP не «безопасен» сам по себе: может удалять проверку, сохранение регистра, запись или побочный эффект. Патч должен сохранять размер, границы, ABI, флаги, целостность кода и быть проверен в **одиночной офлайн-среде**.

## 3.4 Inline hook и trampoline: архитектура, не готовый инжектор

```text
исходная функция: [целые инструкции A,B,...][продолжение]
                          │
             после аккуратного переноса A,B
                          ▼
trampoline: [релокированные A,B] ──► продолжение оригинала
исходный вход: [переход к своей функции] ──► ваш код ──► trampoline (если нужно)
```

[MinHook, R16](#источники) показывает x86/x64 trampoline и обработку инструкций/потоков; [Dobby, R15](#источники) имеет отдельные ARM64 и x86 средства relocation. x86-64 инструкции переменной длины и RIP-relative ссылки требуют корректного декодирования и пересчёта адресов. AArch64 фиксирован по 4 байта, но `B/BL`, `ADR/ADRP`, literal loads и условные ветвления содержат смещения и ограничения дальности; простое копирование пролога ломает код. Нужны сохранение регистров по ABI, корректная генерация ветвей/возврата, cache coherency, согласование потоков и обработка ошибок/W^X. Набор **не** реализует полноценный trampoline или внедрение в сторонний процесс: шаблон даёт отдельно вызываемый memory patch и 16-байтовый ARM64 абсолютный jump, без relocation вытесненных инструкций.

## 3.5 GoldHEN: проверенное подмножество JSON

Исходный файл [GoldHEN Cheat Repository, R13](#источники) и парсер менеджера [R14](#источники) используют поля верхнего уровня `name`, `id`, `version`, `process`, `mods`, `credits`; каждый mod содержит `name`, `type`, `memory`; элемент `memory` — строковые `offset`, `on`, `off` в hex. В репозитории также есть другие типы и дополнительные поля, например `button`, `description` или `hint`. Мы **не нашли опубликованную официальную JSON Schema**. Поэтому `tests/goldhen_generated_subset.schema.json` — строгая **локальная схема только выдаваемого подмножества**, основанная на указанных исходниках, а не официальный норматив для всех GoldHEN-файлов. Тест парсера формы не проверяет работоспособность на реальной консоли.

```json
{
  "name": "Example only - not a real game cheat",
  "id": "CUSA12345",
  "version": "01.00",
  "process": "eboot.bin",
  "mods": [{
    "name": "Example patch - verify address and bytes first",
    "type": "checkbox",
    "memory": [{"offset": "1000", "on": "9090", "off": "89C0"}]
  }],
  "credits": ["Example"]
}
```

Здесь `on` — замена, `off` — байты для отключения. `CUSA12345`, `1000` и байты вымышлены; файл `templates/goldhen_cheat_sample.json` **нельзя** считать читом для реальной игры. Формат имени `CUSA12345_01.00.json`. Документация [GoldHEN Cheat Menu, R17](#источники) указывает `/user/data/GoldHEN/cheats/json/`, а исходник менеджера — `/data/GoldHEN/cheats/json/`; фактический mount/путь проверяйте на своей конфигурации. Меню вызывается удержанием Share по документации проекта. Версии `.json`, `.shn`, `.mc4` — разные форматы; данный генератор выдаёт только JSON.

Пример генерации для **учебного** `demo.bin` из §3.2; этот результат не переносите на PS4:

```powershell
py tools/re_swiss_knife.py --generate-patch demo.bin --arch x86_64 --offset 0x0 `
  --off "48 89 C0" --on "90 90 90" --title-id CUSA12345 --version 01.00 `
  --goldhen-offset 0x1000 --out-dir demo-output
```

Вместо `--offset` можно дать `--aob "48 89 C0 E8 ?? ?? ?? ??"` и опциональный signed `--match-delta 0x0`. Генерация отказывается при нуле/более одного совпадения, несовпадении `off`, разной длине, контейнере, другом ISA и существующих выходных файлах. Для ELF64 можно опустить `--goldhen-offset`: будет вычислен кандидат по §3.1, а его формула записана в `patch_metadata.json`. Для raw dump offset обязателен. В обоих случаях необходимы **точный PS4 x86-64 ELF или самостоятельно проверенный raw dump**, офлайн-игра, совпадение CUSA/версии/модуля и независимая проверка адреса на своей консоли. Генератор не утверждает, что произвольный x86 ELF действительно от PS4.

В `demo-output/` создаются JSON, `offline_file_patcher.py` и `android_patch_template.cpp`. Патчер всегда пишет **новый** файл, проверяет SHA-256 всего входа и исходные байты, не перезаписывает существующие файлы; `--undo` принимает только точную патченную копию:

```powershell
py demo-output/offline_file_patcher.py demo.bin --output demo-patched.bin
py demo-output/offline_file_patcher.py demo-patched.bin --undo --output demo-restored.bin
```

Для **своего PC/Android/произвольного файла** без ложного PS4 JSON используйте `--file-only`: нужны `--offset` либо `--aob`, `--off`, `--on`, `--out-dir`; будет создан только копирующий Python-патчер. Сохранение прав, подписи и работоспособность модифицированного пакета не гарантируются.

## 3.6 Android ARM64 memory patch

`templates/android_arm64_hook.cpp` и генерируемая копия предоставляют `apply_offline_patch(address, expected, replacement, size, original_prot)`. Код не знает адреса приложения и не содержит x86-байты из PS4. Вызовите функцию из **своей** программы только после независимого определения адреса в её ARM64-модуле и оригинальных/новых ARM64-байтов. `expected` проверяется до записи; вызывающая сторона должна гарантировать, что область доступна для чтения, все затронутые страницы отображены и имеют одинаковый переданный `original_prot`, другие потоки не используют страницу, а код patch-функции не расположен на ней. Во время записи EXEC снимается, затем вызывается очистка instruction cache и восстанавливаются permissions. Возможен отказ `mprotect` из-за W^X/политик; `-4` означает, что байты уже изменены, но восстановить protection не удалось. Это не атомарная операция и не полноценный inline hook.

```bash
# На Linux-хосте с установленным NDK; на Windows используйте каталог prebuilt/windows-x86_64.
"$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/linux-x86_64/bin/aarch64-linux-android24-clang++" \
  -std=c++17 -O2 -fPIC -shared -fno-exceptions -fno-rtti -nostdlib++ \
  templates/android_arm64_hook.cpp -o liboffline_patch.so
```

Пример вызова в **собственном экспериментальном приложении**: это демонстрация API, а не патч для какой-либо игры. Адрес и смысл команд нужно установить отдельно; оригинальный NOP не должен совпадать случайно, а страница не должна выполняться во время изменения:

```cpp
#include <cstddef>
#include <sys/mman.h>
extern "C" int apply_offline_patch(void*, const unsigned char*, const unsigned char*,
                                   std::size_t, int);
int patch_owned_example(void* verified_arm64_address) {
    const unsigned char off[] = {0x1F, 0x20, 0x03, 0xD5}; // NOP, только в своём тесте
    const unsigned char on[]  = {0xE0, 0xE1, 0x84, 0x52}; // MOV W0,#9999
    return apply_offline_patch(verified_arm64_address, off, on, sizeof(off), PROT_READ | PROT_EXEC);
}
```

Дополнительно `encode_arm64_absolute_jump(out, capacity, destination)` записывает слова `0x58000051` (`LDR X17,#8`) и `0xD61F0220` (`BR X17`) в little-endian, затем 64-битный адрес: всего 16 байт. `apply_offline_arm64_jump(address, expected, destination, original_prot)` проверяет выравнивание/байты и вызывает тот же API записи. Stub уничтожает X17, не анализирует инструкции пролога и не создаёт переход назад. Для полноценного trampoline необходима корректная relocation PC-relative команд и соблюдение ABI. Макрос `OFFLINE_PATCH_ALLOW_RWX` допускает временный RWX, но ослабляет W^X и может быть запрещён ОС. `OFFLINE_PATCH_ENABLE_CONSTRUCTOR` лишь включает пустую точку инициализации; автоматических патчей нет.

Далее библиотеку необходимо явно подключить к собственному приложению и вызвать API. В локальном ZIP ARM64 `.so` собрана toolchain из зеркала Android NDK r23b (Clang 12, API 24; `source.properties` 23.1.7779620), проверены ELF64, `ET_DYN`, `EM_AARCH64` и экспорт API. Подлинность зеркала не подтверждалась подписью официального архива Google. На телефоне библиотека не запускалась. Host-тест проверяет кодировку, пересечение страниц и ошибки, но не исполняет ARM64. CI настроен найти NDK и собрать и проверить `.so` NDK Clang до упаковки; факт работы конкретного запуска CI нужно проверять отдельно. Android policy, SELinux, concurrency и ASLR требуют испытаний на устройстве. Не соединяйте патч с коммерческой сетевой игрой или античитом.

# 4. Синхронизация и локальное сохранение

## 4.1 Клиентское предсказание и авторитетный сервер

```text
клиент: input(seq=42) ────── UDP/WebSocket ─────────► сервер: проверить input
   │                                                            │
   ├─ сразу предсказать S'[42]                                  ├─ обновить S[42]
   ├─ запомнить inputs 42..N                                     └─ snapshot(tick, ack=42, S[42])
   └─ получить snapshot ◄──────────────────────────────────────────────────┘
       установить авторитетное S[42] → повторить pending inputs 43..N → плавно показать результат
```

Клиент может локально изменять **своё отображение**, но если здоровье/позиция/инвентарь рассчитываются на сервере, следующий authoritative snapshot вернёт серверное состояние или действие будет отвергнуто. Это принцип проектирования, не абсолютная гарантия: часть игр доверяет клиенту, а предсказание может временно расходиться. Потери, перестановка и дубли UDP, задержка, разные версии симуляции и дробная точность тоже вызывают desync — не каждое расхождение является злоупотреблением.

Защитные проверки на доверенном сервере: последовательность и окно повторов, допустимые команды и права, скорость/ускорение/столкновения с учётом времени, типы и границы значений, ограничения инвентаря, rate limits, целостность сессий, журналирование причин отказов и воспроизводимые тесты. Не доверяйте клиентскому `hp=9999` как входной команде. Сравнивайте входные данные с правилами и снимками, допускайте лаг/плавающую точку, разграничивайте сбой клиента и умышленную подмену. Проверки античита ядра и методы их обхода в справочник не входят.

## 4.2 Форматы и инженерия протокола

* **REST/HTTP:** bootstrap/config/profile и относительно редкие транзакции; фиксируйте метод, путь, статус, заголовки, версию схемы, тип и предел тела. HTTPS нужен там, где его ожидает свой клиент; пример ниже без TLS и предназначен только для изолированной лаборатории.
* **WebSocket:** upgrade по HTTP, затем двусторонние frames; используйте подписки, версии сообщений, ping/timeout и ограничение размера. Учебный сервер поддерживает только final masked text/control frames и запрещает браузерный `Origin`.
* **UDP:** datagram может потеряться, дублироваться и прийти не по порядку. Добавляйте sequence/tick, допустимое окно, ограничение размера, retry/ack при необходимости. Проверяйте размеры до выделения памяти, не создавайте усилитель ответов.
* **Protobuf** — формат сериализации, не транспорт и не криптография. Field number + wire type, varint и length-delimited поля позволяют расширять схему; поверх TCP всё равно нужен framing длины, поверх UDP нужен контроль MTU и повторов. Ниже — пример **собственного** контракта, не протокол реальной игры:

```proto
syntax = "proto3";
package localdemo;
message Input { uint32 seq = 1; sint32 dx = 2; sint32 dy = 3; }
message Snapshot { uint64 tick = 1; uint32 ack = 2; sint32 x = 3; sint32 y = 4; }
```

Не делайте вывод «Protobuf» только из бинарных байтов. Документируйте обратную совместимость, кодировку, границы и содержимое; не сохраняйте токены, секреты, персональные данные или пакеты действующего коммерческого сервиса.

## 4.3 Локальный демонстрационный REST/WS/UDP сервер

`templates/local_ps4_server_emulator.py` — **синтетическая заготовка**, а не эмуляция PSN или протокола какой-либо PS4-игры. Только один анонимный игрок, состояние в памяти; принимает команды `move` (`seq`, `dx`, `dy`), проверяет диапазоны и последовательность, затем сам изменяет координаты. Сервис не имеет TLS, входа, хранения, полноценной защиты, сетевого стека игры или NAT traversal. Нельзя ожидать, что retail-игра автоматически к нему подключится.

```powershell
py templates/local_ps4_server_emulator.py
# Следующие команды выполните в отдельном терминале:
Invoke-RestMethod http://127.0.0.1:8765/health
Invoke-RestMethod -Method Post -ContentType 'application/json' -Body '{"type":"move","seq":1,"dx":1,"dy":0}' -Uri http://127.0.0.1:8765/input
Invoke-RestMethod http://127.0.0.1:8765/state
```

Для Linux/macOS используйте `curl -H 'Content-Type: application/json' -d '{"type":"move","seq":1,"dx":1,"dy":0}' http://127.0.0.1:8765/input` в отдельном терминале.

UDP-пример: после приведённого REST-вызова используйте новую `seq`:

```python
import json, socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(2)
s.sendto(json.dumps({"type":"move", "seq":2, "dx":0, "dy":1}).encode(), ("127.0.0.1", 8766))
print(json.loads(s.recv(1024)))
```

WebSocket-пример для **дополнительного** пакета `websockets` (`python -m pip install websockets`); у сервера дополнительных зависимостей нет. Новый seq, `Origin` не задавать:

```python
import asyncio, json, websockets
async def demo():
    async with websockets.connect("ws://127.0.0.1:8765/ws") as ws:
        await ws.send(json.dumps({"type":"move", "seq":3, "dx":-1, "dy":0}))
        print(await ws.recv())
asyncio.run(demo())
```

По умолчанию слушает только `127.0.0.1`. Для собственного PS4-клиента в **изолированной** локальной сети можно явно использовать конкретный адрес Windows-хоста, например `--bind 192.168.1.20 --allow-lan`; откройте доступ только доверенным устройствам в firewall и не публикуйте порты. `0.0.0.0`, публичные IP и LAN без явного разрешения сервер отвергает. Передача не защищена и не аутентифицирована; не вводите настоящие пароли/токены. Для игры нужен её документированный/разрешённый способ настройки адреса и собственная реализация её схемы, TLS и поведения; если клиент этого не поддерживает, данный пример сам по себе не восстановит работу. Обход pinning, PSN/DRM и перенаправление действующих коммерческих сервисов не рассматриваются.

## 4.4 Как исследовать сохранение backend без атаки на действующий сервис

1. Установите статус проекта/службы и право на интероперабельность. Работайте с публичной документацией, опубликованным исходником, собственным тестовым клиентом и искусственными данными в лабораторной сети.
2. Начните с моделирования конечных состояний: bootstrap → локальный профиль → доступные режимы → вход → input/snapshot. Контракт и fixture-ответы снабдите версиями и отрицательными тестами.
3. Выделите REST, сокеты и симуляцию в отдельные интерфейсы; применяйте bounded queues и timeouts. Для надёжного хранения в собственном проекте добавьте миграции, журнал транзакций, резервные копии и авторизацию. Шаблон из комплекта этого не делает.
4. Для каждой команды проверяйте schema, limits, идемпотентность и допустимость перехода. Тестируйте дубли, перестановку, потерю и disconnect/reconnect, сравнивая сохранённый authoritative state.
5. Запускайте сначала на loopback; затем только в изолированной LAN. Используйте собственные тестовые имена/сертификаты там, где это поддерживается **вашим** клиентом, а не методы обхода защиты чужого клиента.

[OpenSpy Core, R19](#источники) разделяет сервисы на процессы, использует HTTP/AMQP/Redis и описывает отдельные сетевые драйверы и асинхронные задачи. [Dreadnought Revival, R20](#источники) демонстрирует проект сохранения **конкретной PC-игры**: gateway, профиль/инвентарь, matchmaking и отдельные игровые процессы. Это примеры архитектуры, не обещание PS4-совместимости данного шаблона; конкретные зависимости и правовые условия проекта следует читать отдельно.

## Проверка качества этого набора

```bash
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
```

Тесты используют синтетические ELF, SELF/FSELF, NSO0 и FMF, проверяют формулу и неоднозначность PT_LOAD, декодирование LZ4/zlib/zstd, SHA-256, проверку путей/коллизий, GoldHEN-подмножество, откат, host-компиляцию C++ и HTTP/WS/UDP. Дополнительно проверен один открытый FM23-совместимый архив шрифтов (R27), не включённый в набор. Тесты не подтверждают работу на PS4 или Android-устройстве, все ревизии FMF или совместимость игры. ZIP может быть воспроизводимо собран с локальной NDK-библиотекой; настроенный Linux CI требует собственной NDK-сборки перед упаковкой.
